## Техническая спецификация: Расширение pi-strata для Pi Coding Agent## 1. Общее описание и цель

pi-strata — это расширение для Pi Coding Agent, оптимизирующее управление контекстом при работе с локальными LLM (через llama.cpp / Ollama).
Главная цель: Обеспечить высокое переиспользование KV-кэша (Prompt Caching) в llama.cpp. Это достигается за счет формирования иммутабельного (неизменяемого), послойно растущего префикса контекста. Расширение исключает из истории сообщений эфемерный «мусор» (сырые логи терминала, промежуточные ошибки), заменяя их компактными техническими отчетами, которые дописываются строго в конец кэшированного блока
------------------------------

## 2. Архитектура контекста (Strata Layout)

Для сохранения KV-кэша структура финального промпта, отправляемого в llama.cpp, должна быть строго последовательной. Изменение даже одного пробела или символа в верхних слоях сбрасывает кэш.

Данные слоёв 1-3 хранятся не в файлах, а в самом разговоре: модель записывает каждую фазу между уникальными маркерами, а расширение вычленяет блоки алгоритмически (регулярное выражение). Последнее вхождение блока каждого типа побеждает: при обновлении фазы модель пишет полную новую версию между новыми маркерами. Новый блок RESEARCH или PLAN начинает новый цикл задачи: все блоки STEP-N, стоявшие раньше него в разговоре (отчёты предыдущего цикла), отбрасываются — новая задача не наследует отчёты старого плана. Отчёты STEP-N append-only только в пределах одного цикла.

[Слой 0] Системный промпт (Роль, правила, гайдлайны + инструкции pi-strata)
  └── [Слой 1] Блок /*STRATA::RESEARCH::v1*/ (Исследование: стек, архитектура, вводные)
        └── [Слой 2] Блок /*STRATA::PLAN::v1*/ (План работ: TODO-лист, актуальный статус задач)
              └── [Слой 3] Блоки /*STRATA::STEP-N::v1*/ (История отчетов: выполненные шаги, append-only)
                    └── [Текущий слой] Текущая задача + вывод инструментов (эфемерный)

Summary после компактизации = маркерная строка + извлеченные блоки в фиксированном порядке (RESEARCH, PLAN, STEP-1..N), склеенные строго через \n\n. Поскольку summary сама состоит из маркированных блоков, следующая компактизация извлекает слои из (summary + новые сообщения) тем же регулярным выражением — идентичный префиксный контекст восстанавливается без хранения слоёв в файлах.

При компактизации, не связанной с завершением этапа (переполнение, ручная), после блоков в summary добавляется стандартная LLM-суммаризация pi по эфемерному контексту (см. §5). Она находится ПОСЛЕ всех блоков и не входит в стабильный префикс: при следующей компактизации извлекаются только блоки, а хвост суммаризации либо обновляется тем же механизмом pi (итеративное слияние), либо отбрасывается при завершении этапа.

## 3. Функциональные требования и Пайплайн работы## Этап 1: Инициализация и Исследование (on_init_task)

   1. Агент ведет диалог с пользователем, уточняя требования.
   2. После фиксации задачи агент пишет отчёт исследования между маркерами /*STRATA::RESEARCH::v1*/ … /*STRATA::END::RESEARCH::v1*/. В начале отчёта обязательно даётся краткая суммаризация задачи, полученной от пользователя: цель, ожидаемый результат и явно заданные ограничения. Затем фиксируются стек, архитектура, вводные, ограничения и критерии готовности. Компактизации на этом этапе нет — агент сразу переходит к планированию.
   3. Новая задача: если пользователь после завершения плана дал следующую задачу, цикл начинается заново с этого этапа (новый RESEARCH и новый PLAN). Все STEP-N, стоявшие раньше нового RESEARCH/PLAN, отбрасываются автоматически — новый цикл стартует с чистой историей шагов.

## Этап 2: Планирование (on_plan_generation)

   1. На основе исследования модель формирует атомарный TODO-лист.
   2. Каждый пункт плана должен быть самодостаточным и достаточно подробным: после компактизации контекста шаг выполняется по своему пункту, не перечитывая историю, поэтому в пункте фиксируются затронутые файлы/модули, конкретные действия, команды проверки и ожидаемый результат — по плану должна быть возможна полная реализация задачи.
   3. План записывается между маркерами /*STRATA::PLAN::v1*/ … /*STRATA::END::PLAN::v1*/ (TODO-лист: формат «- задача», по пункту на строку).
   4. Модель вызывает strata(action="advance"); в конце хода производится первая компактизация контекста: поверх слоя 0 добавляются блоки RESEARCH и PLAN.

## Этап 3: Исполнение шага и Компактизация (on_step_complete)

После того как агент выполнил очередной пункт плана (например, написал код и запустил тесты):

   1. PLAN сохраняется в исходном виде. Статус выполнения определяется по наличию отчётов STEP-N.
   2. Запись отчета: Модель пишет компактный технический отчёт шага N (что сделано, файлы, результаты тестов, решения, риски) между маркерами /*STRATA::STEP-N::v1*/ … /*STRATA::END::STEP-N::v1*/.
   3. Модель вызывает strata(action="advance", step=N); в конце хода производится компактизация контекста: поверх слоя 0 добавляются актуальные блоки RESEARCH, PLAN и новый STEP-N.
   4. Весь эфемерный контекст шага (за исключением неизменяемой части - отчетов с предыдущих шагов, плана и исследования) перед компактизацией сохраняется расширением в файл <сессия>.pi_strata/tmp/step_N_raw.md. Упоменание о нём должно быть в отчёте, чтобы LLM на следующем шаге могла туда посмотреть.

## 4. Технические ограничения и Требования к Форматированию

   1. Иммутабельность строк: выделение блоков и склейка summary должны использовать строго фиксированные маркеры и разделители (ровно два переноса строки \n\n). Любая динамическая вставка запрещена, префикс должен строго посимвольно сохраняться. Стабильный префикс — это [системный промпт + блоки слоёв]; динамическая часть (LLM-суммаризация при §5, хвот сообщений) всегда следует после блоков.
   2. Маркеры уникальны: /*STRATA::<FAZA>::v1*/ … /*STRATA::END::<FAZA>::v1*/, где FAZA = RESEARCH | PLAN | STEP-N. Токены не должны встречаться в обычном коде; незакрытые блоки и блоки с пустым телом отбрасываются.
   3. Изоляция текущих логов: Вывод текущих команд терминала, который генерируется прямо сейчас, должен крепиться строго в самый конец промпта. По завершении шага этот вывод стирается и превращается в блок STEP-N в слое 3.

------------------------------

## 5. Компактизации, не связанные с завершением этапа (переполнение / ручные)

    Strata-компактизация (детерминированный layer-dump) выполняется только по завершению этапов: первая — после плана, далее — после каждого шага.

    Любая другая компактизация (переполнение контекста, ручная) для strata-сессии сохраняет strata-секции и поверх них использует стандартную суммаризацию pi:

    1. Summary = блоки слоёв (детерминированная сборка, посимвольно как в §2) + стандартная LLM-суммаризация pi по эфемерному контексту (те же промпт, merge-семантика previous-summary и учёт файловой истории, что и в pi без расширения). Так незавершённая работа не теряется и продолжает накапливаться как обычный checkpoint pi.
    2. LLM-суммаризатор НЕ получает блоки слоёв: входом для merge является только собственный хвост предыдущей суммаризации (часть summary после блоков), а в промпт добавляется инструкция не повторять STRATA-блоки, встречающиеся в сыром разговоре. Это гарантирует, что стабильный префикс [системный промпт + блоки] не проходит через LLM и не мутирует.
    3. Fallback: если модель не выбрана, авторизация недоступна или вызов LLM упал — summary остаётся детерминированным layer-dump (без хвоста суммаризации), компактизация не прерывается. Отмена (abort) компактизации, напротив, пробрасывается.
    4. Хвот, который держит pi (firstKeptEntryId), не меняется: незавершённая работа в пределах бюджета keepRecentTokens остаётся в контексте как есть.
    5. Конфликты с другими расширениями: если другое расширение тоже обрабатывает session_before_compact, pi использует результат последнего загруженного обработчика (merge нет). Strata помечает свой результат маркером details.strata и после компактизации проверяет сохранённую запись: если результат заменил чужой обработчик, пользователю выводится предупреждение (причина + совет оставить один обработчик компактизации либо грузить pi-strata последним). Обратный случай (strata загружен позже и вытеснил чужой результат) детектировать невозможно — публичный API не даёт перечислить обработчики других расширений.
